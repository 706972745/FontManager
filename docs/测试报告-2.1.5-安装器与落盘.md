### 5. 插件不丢（R-02）

- 代码：`plugins.rs:372-384` 的 `legacy_plugins_dir()` = `store::legacy_app_data_dir().join("plugins")`，而 `legacy_app_data_dir()` 走 `dirs::data_dir()`（Windows）⇒ `%APPDATA%\FontManager\plugins`，**不是** `data\plugins` ✅
- 运行时（第 3 次启动日志，逐字）：
  ```
  [plugin] 自动启用「com.fontmanager.font-apply」失败：没找到插件…；目录：E:\…\rust-target\release\plugins
  ```
  解析结果是 `<exe>\plugins`（构建产物目录），**不是** `<exe>\data\plugins` ✅
- 为什么不会误判：`resolve_plugins_dir()` 的规则是"老位置有插件 && 新位置没有 → 沿用老位置"，如果 `legacy_plugins_dir()` 漂到 `data\plugins`，这个判据两边都空 → 落到 `<exe>\plugins`；而**默认安装时 `<exe>\plugins` 就是用户原来的插件目录**（`%LOCALAPPDATA%\FontManager\plugins`，本机 674 KB / 2 个插件，21:xx 检查仍在）⇒ 默认安装的用户升级后插件照常可见。
- **已知边界（非本次回归）**：如果用户"卸载后**重装到另一个目录**"，插件仍留在 `%LOCALAPPDATA%\FontManager\plugins`，新目录的 `<exe>\plugins` 是空的 → 界面上看不到插件（文件没丢）。2.1.4 同样如此（插件一直跟安装目录走），不是 2.1.5 引入。建议在验收说明里写一句，或后续版本把"旧安装目录的 plugins"也加进收养范围。

## 4. C. 数据根判定与回退

### 13. 四级判定顺序（`store.rs:447-530`）与 `OnceLock`

顺序**不能变**，且每一级都有"为什么"写在注释里：

| 级 | 条件 | 结果 | 日志 `source=` |
|---|---|---|---|
| 0 | `ZFM_DATA_DIR` 存在、**绝对路径**、且写探针成功 | 用它（排障/自动化） | `env` |
| 1 | `<exe>\data` 已存在，且里面已有 `state.json` / `.zfm-data-root` / `.zfm-migrate-in-progress` | **锚定**，不再探测（防止"今天管理员能写、明天不能写"导致数据一分为二） | `install` |
| 2 | `<exe>\data` 写探针成功 | 建它 | `install` |
| 3 | `%LOCALAPPDATA%\FontManager\data` 写探针成功 | 回退 | `localappdata` |
| 4 | 全都失败 | `%APPDATA%\FontManager`（宁可留 C 盘，也不让软件因没地方写而崩） | `roaming(fallback)` |

- `OnceLock` 只锚定一次（`data_root_cached()`）：`diag::log()` 每次写日志都要问路径，而探针要 `create_dir_all + write + delete`；更要紧的是**同一进程内路径不允许变**，否则 state.json 会写到两个地方。
- `MIGRATION_FAILED` + `effective_data_root()` 是"第二次真相"：迁移失败时把本次数据根钉回老位置（`OnceLock` 天生不可写，所以用两个静态量分工）。

**"装到 Program Files、普通权限跑"的推演**（本机无法真装，用代码 + 单测说明）：
- 安装器侧：`hooks.nsh` 先 `CreateDirectory "$INSTDIR\data"`，再在 `$INSTDIR\.zfm-data-probe` 写探针 → 失败 → `DetailPrint "安装目录当前用户不可写，运行时数据将回退到 %LOCALAPPDATA%\FontManager\data"`，**不写** `.zfm-data-root`；
- 程序侧：`<exe>\data` 不存在或虽存在但写不进 ⇒ 落到第 3 级 ⇒ 数据在 `%LOCALAPPDATA%\FontManager\data`，启动日志打 **`source=localappdata`**；
- 设计里"默认安装目录 = `%LOCALAPPDATA%\FontManager`，所以第 3 级与第 2 级指向同一目录"这条特意选择，保证了回退不会产生第二份数据。

单测覆盖（`store.rs:1452-1514`，4 条，`env_lock()` 串行）：`data_root_env_override_wins`、`data_root_env_ignores_relative_path`、`data_root_env_ignores_unwritable_path`、`data_root_falls_back_to_legacy_in_debug_build`，另有 `probe_writable_cleans_up_after_itself`。
**诚实说明：第 1/3 级（安装目录已存在 / LOCALAPPDATA 回退）没有单测**——它们依赖真实盘符权限，单测只能"造一个不可写目录"，作者用上面的探针单测间接覆盖了判定原语。A-13 说的"4 个判定顺序用例"实际覆盖的是第 0 级与 debug 兜底，不是全部四级。

## 7. 发现的问题（按严重度）

### 发现 1（P1，建议交付前改；路由 → 工程师）

**升级维护页：默认选中的是"先卸载再安装"，而"（推荐）"标在第二个选项上。**

- 证据：`PageReinstall` 里 `${If} $ReinstallPageCheck <> 2 → SendMessage $R2 ${BM_SETCHECK}`（选中**第一个** radio）；升级分支第一个 radio 的文案是 `$(uninstallBeforeInstalling)` = "先卸载再安装"，第二个才是 `$(dontUninstall)` = "直接覆盖安装（推荐）"。
- 后果：用户升级时直接点"下一步"= 走**卸载**分支。卸载成功、安装失败时用户手上没有软件（数据还在）——正是 R-18 描述的"用户没软件了"，只不过触发点从"文案对调"变成了"默认值"。
- 说明：默认选第一个 radio 是 **Tauri 上游行为**，2.1.4 也这样，所以**不是 2.1.5 引入的回归**；但 2.1.5 给另一个选项加了"（推荐）"标签，于是"推荐项不是默认项"，自相矛盾，比不改更迷惑。
- 建议改法（4 行之内，不动 $R1/$R2/$R3 的语义映射）：在 `PageReinstall` 的"升级/降级"分支里，把默认勾选换成 `$R3` 并设 `StrCpy $ReinstallPageCheck 2`；两种改法都不许碰 `PageLeaveReinstall` 的 `$R1` 分支。

### 发现 2（P2，建议改或至少在验收说明写明；路由 → 工程师/架构）

**首次升级后启动，窗口出现前会阻塞 2.5 分钟（删旧缓存）。**

- 实测（本机，383 MB / 332 个文件的 preview-cache）：从进程启动到写出第一行启动日志 **151 秒**，期间 `data\` 里已经搬完数据，但**界面完全不出现**（`store::load()` 在 `tauri::Builder` 之前，`lib.rs:2768`）。删除速率约 2.6 MB/s。
- 数据安全没问题：账本已落盘、迁移标记已删，用户此时强杀也不会丢数据（下次启动走幂等出口）。**纯粹是体验**：用户会以为"没装上/打不开"，反复双击（第二实例只写 `open-request.txt` 后退出，更让人确信"点了没反应"）。
- 建议：把步骤 ⑧ 的缓存清理挪到"界面起来之后"的后台线程（或干脆只删 `thumb-cache`、`preview-cache` 交给 LRU 自然淘汰），并在日志/首次启动提示里说明"正在清理旧缓存，预计 1~3 分钟"。
- 附注：设计文档把"删缓存"的理由写成"可重建、不占迁移时间"，但没有预算**删除本身的耗时**；实测在装了杀软的生产机上这个耗时是分钟级。
