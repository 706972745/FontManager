# 多软件共用插件库 · 契约（2026-11-26）

FontManager 与 AssetManager 共用**同一个**插件库，靠 **ID 前缀**区分归属。
本文是这份契约的唯一出处：registry 脚本、客户端代码、面板发布都按这里来。

## 一、两个仓库

| 仓库 | 内容 | 谁推 |
|---|---|---|
| `706972745/Manager-Plugin` | **官方插件**源码 + release 里的 zip | 官方（本机推送） |
| `706972745/Manager-Workshop` | **社区插件**目录 + 聚合清单 + 面板发布包 | 社区 PR + 聚合脚本 |

> 2026-11-26 由 `FontManager-Plugin` / `FontManager-Workshop` 改名而来。
> GitHub 对旧名做 301，但**代码里一律写新名**，不依赖重定向。

## 二、前缀表

| 前缀 | 软件 | 官方件目录（Manager-Plugin） | 清单切片 |
|---|---|---|---|
| `FM` | FontManager | `FM-FONT-SYNC/`、`FM-FONT-STAT/`… | `by-app/fm.json` |
| `AM` | AssetManager | `AM-…/`（尚未建立） | `by-app/am.json` |

- 前缀**必须大写**，是软件的编号，不是可选写法。
- 两段各自是任意长度的字母或数字（大小写随意），整串 ≤ 40。
- 正则（registry 校验、客户端过滤、CI 共用同一条）：

```
^FM-[A-Za-z0-9]+-[A-Za-z0-9]+$      # FontManager
^AM-[A-Za-z0-9]+-[A-Za-z0-9]+$      # AssetManager
^(FM|AM)-[A-Za-z0-9]+-[A-Za-z0-9]+$ # registry 侧的联合闸门
```

## 三、清单切片（客户端只拉自己那份）

`aggregate_index.py` 产出两类文件：

```
index.json          全量（跨软件），给维护者看 / 兼容旧客户端
by-app/fm.json      只含 FM-* 条目，FontManager 客户端唯一请求
by-app/am.json      只含 AM-* 条目
```

- 结构**与 index.json 完全一致**（`version` / `generatedAt` / `official` / `plugins`）。
- 某前缀一条都没有时**也要写**（空数组），否则客户端 404。
- 客户端 URL：

```
https://raw.githubusercontent.com/706972745/Manager-Workshop/main/by-app/fm.json
```

- **不该看到的条目根本不会进内存**：别的软件的插件、命名不合规的条目都在聚合时被分桶挡掉。

## 四、面板发布资产（按软件分开命名）

面板是同一个代码库的产物，但两个软件的面板互不覆盖：

| 资产 | 用途 |
|---|---|
| `panel-fm.zip` | FontManager 面板产物 |
| `panel-fm-meta.json` | 上者的 `{version, sha256, size}` |

- 都放在 `Manager-Workshop` 的 **v1 release** 下（release 资产不走 CDN 缓存，这是当初选它的原因）。
- 根目录 `panel-fm-meta.json` 与 release 资产保持同内容，由 `sync-panel-meta.yml` 校验后同步。
- AssetManager 将来直接加 `panel-am.zip` / `panel-am-meta.json`，互不影响。

## 五、官方件发布

- 目录名 = ID，zip 资产名 = `<ID>.zip`，带版本别名 `<ID>-<version>.zip`。
- `official.json`（在 Manager-Workshop）是官方区的**手工清单**，`download` 指向
  `https://github.com/706972745/Manager-Plugin/releases/download/v1/<ID>.zip`。
- 官方件同样受前缀闸门约束 —— 不因为「官方」就放行别的命名。

## 六、ID 迁移对照表

| 旧 ID | 新 ID |
|---|---|
| `com.fontmanager.font-sync` | `FM-FONT-SYNC` |
| `com.fontmanager.example.font-stats` | `FM-FONT-STAT` |
| `com.fontmanager.example.specimen-export` | `FM-FONT-SPEC` |
| `com.fontmanager.font-apply` | `FM-FONT-APPLY` |
| `com.example.hello-plugin` | `FM-DEMO-HELLO` |
| `font-renamer`（社区） | `FM-FONT-RENAME` |
| `spec-counter`（社区） | `FM-FONT-COUNT` |

### 插件内部的持久化键**不跟着改**

`font-sync` 的令牌存在 Windows 凭据管理器 `FontManager/font-sync/vault`，
快照索引在 `%APPDATA%\FontManager\font-sync\`。这些是**用户数据的位置**，
和「插件叫什么名字」是两件事：

- ID 改了 → 安装目录名变了；
- 存储键**保持不变** → 老用户升级后令牌、同步状态全都还在，不用重新登录。

以后新增插件也照此办理：ID 是身份，存储键是数据契约，两者不联动。

## 七、上线顺序（不能反）

1. registry 与官方件先改（`Manager-Workshop` 生成 `by-app/fm.json`、`official.json` 指向新资产）；
2. 官方件 CI 重新打包，v1 里出现 `FM-*.zip`；
3. **最后**发新面板（`panel-fm.zip` + `panel-fm-meta.json`）。

反过来的话，新客户端拉 `by-app/fm.json` 会 404，插件中心空着。
