### 复现步骤（缺陷 D-1）

1. 冷启动一个 4000+ 族的库，等种子首帧出现（此时后台仍在全量读取）。
2. **读取期间**把 X 族停用 → `noteOverrides([X], false)`，`overrides = {X: false}`。
3. 全量落地 `applyFullScan()` → X 显示停用（正确），`overrides` 仍保留 `{X: false}`（`pruneOverrides` 只裁掉「已不存在的路径」）。
4. 读取结束后（`phase === "ready"`）用户再把 X 启用 → `noteOverrides` **因 phase 不是 scanning 直接 return**，`overrides` 不变。
5. 触发任意一次 rescan（导入字体 / watcher / 手动刷新 / 换库 / 启停失败回滚）。
6. 扫描 2 的 probe 看到 X 已注册（`active = true`），但 `applyOverrides` 用第 3 步留下的 `X→false` 把它压回停用。

**结果**：界面显示 X 停用，注册表里 X 其实是启用的。用户在设计软件里能用它、在 FontManager 里看到的却是停用；反向（`X→true` 残留）更糟 —— 界面说已启用，实际套用失败。状态会一直错到下次重启或又一次全量。

**失败断言原文**（`tests/seedOverrides.test.ts:123`）：

```
not ok 272 - overrides from a finished scan must not win again in the next scan
  error: 扫描 1 的覆盖项被带进了扫描 2：下一轮全量会用它压过真实注册表状态，
         界面从此长时间显示错的启用状态（见 fontStore.ts:1858 只裁剪不清空）
  1 !== 0
  expected: 0
  actual: 1
```

**涉及代码**：

```ts
// src/state/fontStore.ts:1848
applyFullScan: (full) => {
  const s = get();
  const merged = applyOverrides(full, s.overrides);
  set({
    fonts: merged,
    phase: "ready",
    fullScanDone: true,
    // ← 这里只裁剪，不清空
    overrides: pruneOverrides(s.overrides, full.map((f) => f.path)),
  });
},
```

**建议修法**（仅供参考，QA 不改源码）：`overrides: new Map()`。覆盖项的生命周期就是「一次扫描」—— 落地那一刻它已经被消费掉了，留着没有任何正向作用。这同时对齐设计 §3.3 原文「只在 `phase === "scanning"` 期间非空，`applyFullScan` 之后清空」（当前实现跟的是 §5.4 的骨架代码，两处文档自相矛盾，建议一并改 §5.4）。

## 4. 未覆盖到的风险（诚实说明）

1. **首帧体感 / 1.5s 预算（AC-01、G1、M1、M2）无法验证**：无 GUI 运行环境，且 `seedReadyMs` 埋点没有落进日志（设计 §10-9 建议的计时口径也未最终确认）。我只能从代码侧确认「种子在 `scan_all` 之前同步发出」这条时序成立，**实际毫秒数必须由有桌面环境的人用秒表 + `[seed]` 日志实测**。
2. **注册表真实写入行为未验证**：所有 `apply` / `apply_cached` 路径（`AddFontResourceW`、HKCU 写入、`WM_FONTCHANGE`）都没有跑过实测。`record=false` 的 14 个调用点我只能保证**代码取值与语义表一致**，无法证明「启用至关闭退出后注册表确实被还原」。
3. **`store::load()` 对台账系统路径的兜底清理（§9.1 U17）没有单测**：`load()` 读写的是真实应用数据目录，无法在单测里隔离。已改为按代码核对（`store.rs:519-537`，`retain(!is_system_font)` + 变更即 `save`）。
4. **`UI_SEED_SENT` 每进程只发一次**：无法用单测证明（需要 `AppHandle` 与真实 `emit`）。只验证了「守卫位置正确」与「HTTP 侧不触碰它」两点，端到端只能靠 M21 手工回归。
5. **滚动位置（AC-09）与「骨架屏只出现一次」（AC-07）只能手工录屏**：代码侧确认了「不清空 `fonts`、不换 `key`、条件改 `fonts.length === 0`」，但「像素保持」的实际偏差、以及排序键变化导致的视口漂移只能靠 M6 / M7 / M8 手工判定。设计 ADR-07 已把「不做族名锚点」列为显式偏差，本报告不重复判罚。
6. **跨平台语义**：`norm_path`（`activation.rs:76`）在所有平台都做 `to_lowercase()` + `/`→`\`。Linux/macOS 是大小写敏感文件系统，两个仅大小写不同的文件会被去重成一份。当前产品是 Windows 桌面端（`tauri.conf.json` 只配 Windows 打包），**本版本无实际影响**；若将来做跨平台，这里是必须改的口子。
7. **`LoadProgress` 的 1.5s「已就绪」淡出、9 语言切换（M23）** 只做了静态核对（key 齐、无硬编码），没有真实渲染。
8. **`rescan()` 单飞行（single-flight）与并发启停的竞态（C6）** 未压测；只按代码核对了「都走 `store.0.lock()`」这一点。
9. **性能**：`sync_batch` 的记账实现是 `for path in done { state.record_activated(path, active) }`（`activation.rs:170-174`），而 `record_activated` 内部有一次 `self.activated.iter().any(|p| ... norm_path(p) ...)`（`store.rs:213`）—— 这是 **O(批大小 × 台账长度)**，与设计 §5.2 承诺的「先批量剔除再批量插入，一次遍历搞定」不符。实测台账 ~1000 条、批 200 条时约 20ms/批，混在 35~45 分钟的批量启停里可忽略，**不构成性能 Bug**，但台账若真涨到几千条会开始可测。建议下一版顺手改掉。
