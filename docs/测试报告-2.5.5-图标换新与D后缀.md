### 1.2 我自己修掉的测试写法问题（1 处，如实记录）

用例 1 我最初写死「每帧必须含**全透明**像素（alpha==0）」，结果应用图标 16px 那帧报 `clear_ratio=0.00%` 被判失败。**查证后是我的断言错，不是产物错**：

```
app icon 16px:  min_alpha=33  count(alpha==0)=0  alpha<=8: 0  half_ratio=7.03%
app icon 24px:  min_alpha= 0  count(alpha==0)=4
app icon 256px: min_alpha= 0  count(alpha==0)=1290
```

应用图标是**满版白色圆角底板**（`make-icons.py` 的 `full_bleed=True`，不裁边）。缩到 16×16 时，圆角只剩 3~4 px 的三角区，采样点全部落在抗锯齿的中间值上（min alpha=33），因此「alpha 恰好为 0 的像素」天然为 0 —— 但该帧**确实有 7.03%（18 px）半透明像素**，alpha 通道是有效的。断言已改为「必须有 `alpha<255` 的像素」（即 `clear+half > 0`），这才是「这帧真的有透明」的正确判据。

> 这条记在这里是为了让别人能复现我的判定口径：**应用图标 16px 没有 alpha=0 的像素不是缺陷**，谁要拿「全透明像素数」当门禁会误报。

## 9. 用例 8 · 16px / 24px 可读性

产出（按要求路径）：

- `FontManager/_tmp/icon-render/qa-小尺寸.png` —— **按真实像素、未放大**（16px 列 / 24px 列，另附一条「模拟资源管理器列表行」白底带文件名）
- `FontManager/_tmp/icon-render/qa-小尺寸-8x.png` —— **8 倍最近邻**放大对照

### 9.1 结论（不含糊）

> **16px：不能可靠区分**三枚文件图标（`.S` / `.P` / `.D`）。
> **24px：能区分。**

### 9.2 依据

**定量**（蓝色墨迹掩膜 = `alpha>32 且 b>130 且 b-r>25`，即「真正画了字的地方」）：

| 尺寸 | S 墨迹 px | P 墨迹 px | D 墨迹 px | S vs P IoU | S vs D IoU | P vs D IoU |
|---|---|---|---|---|---|---|
| 16px | 26 / 256 | 30 / 256 | 26 / 256 | **0.400** | 0.209 | 0.143 |
| 24px | 72 / 576 | 59 / 576 | 61 / 576 | 0.351 | 0.255 | 0.188 |
| 256px | 6077 | 5130 | 4276 | 0.248 | 0.121 | 0.122 |

- 16px 下每枚只有 **26~30 个蓝色像素**，字母标（主字母 + 上标 F 的叠加）被压成 ~7×6 px 的一团。
- **S 与 P 的墨迹重叠 IoU = 0.400**，是全部对比里最高的；两者的唯一结构差异是「P 有一条 4 px 的连续左侧直笔、S 没有」，差 3~4 个像素。
- 24px 下墨迹增到 59~72 px，三枚的轮廓分得开：**S = 纯斜笔**、**P = 左侧连续直笔 + 右上碗形**、**D = 下方大碗 + 右侧灰色第二张纸阴影**。

**定量佐证（逐像素 ASCII dump，16px，可复现）**：

```
16px  '#'=蓝墨迹   '.'=有像素非蓝   ' '=全透明
        S(快照)                    P(整包)                    D(数据)
r3      ........##            ............              ............
r4      .....###..             ......###..               ....###.....
r5      .....###..             ......###..               ..#####.....
r6      ..#####...             #..#####...               ..####......
r7      ...##.....             #..####....               #.####......
r8      ....#.....             #...#.....                ..#.........
r9      ..........             #.........                ............
```
→ S 是一条从右上到左下的斜带（**没有**左侧直笔）；P 在 x=0 有连续 4 行 `#`（左侧直笔）；D 的碗更低、左笔只有 1~2 px 且不连续。

**定性（盲测）**：把 16px 三枚按**打乱顺序**排成 A/B/C（顺序 = D, S, P，图里不标真值）交给视觉模型判读，返回的是「一团蓝色笔画」，**未能读出 S / P / D 任何一个字母**（图：`_tmp/qa-icon-verify/blind-16px.png`）。

### 9.3 定性判定：**风险提示（Q2），不是规格违反**

- `docs/图标规范.md:25-26` 只承诺「**手写小字**只用来说明这个文件是干什么的，16px 下看不出来属于正常」，**没有**承诺字母标在 16px 可辨。
- 所以从「文档承诺」看：**不违反**。
- 但从原始目标「资源管理器里一眼认出这几个东西是一家的（且互不混淆）」看：16px 下 S/P 需要凑近逐像素比较才能分开，**离目标有距离**。三枚里只有 D 靠「右侧灰色第二张纸」这条非字母线索能在 16px 稳定区分。
- 结论我给到「不能可靠区分」，去留交 owner。**若要求 16px 可辨**，方向是加大主字母在 16px 档的字号/降低上标 F 的干扰/去掉叠加，属设计改稿，非本轮实现错误。

### 9.4 顺带记录：应用图标 16px 的观感

应用图标 16px 是满版白底板 + 花体 `FM`，8 倍放大后可辨为「一坨蓝色花体」，**字母辨识度与四枚文件图标同档**（也是 16px 只看得见色块）。同理不算缺陷（`FM` 是品牌花字，不承担小尺寸识别任务）。
