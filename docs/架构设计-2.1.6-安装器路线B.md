## 0. 现场核实（本次设计的硬事实，逐条带出处）

> 设计前把「2.1.5 到底写了什么」全部拉出来对过一遍。**下面 8 条与 PRD/规格书的口径有出入，以本节实测为准**（v2 新增 0.7 的补充与 0.8 的工具链事实），已同步进 PRD 的修正建议。

### 0.1 安装包的真实内容：2.1.5 是 **2 个文件**；2.1.6 是 **3 个**

| 证据 | 结论 |
|---|---|
| `rust-target/release/nsis/x64/installer.nsi:960-966` 渲染后 `{{#each resources_dirs}}` / `{{#each resources}}` / `{{#each binaries}}` 三个循环**全部为空** | 安装器只写 `fontmanager.exe` |
| 同文件 `:989` `WriteUninstaller "$INSTDIR\uninstall.exe"` | 2.1.5 共 **2 个文件** |
| `HKCU\...\Uninstall\FontManager` 的 3 个 `.ico`（`data-icon.ico` / `pack-icon.ico` / `snapshot-icon.ico`，实测 114,208 + 63,265 + 55,809 B）在**程序首次运行后**才出现 | 它们由主应用 `library_marker.rs` / `folder_export.rs` 运行时生成，**安装器不写** |
| 实测 `%LOCALAPPDATA%\FontManager` 目录清单：`fontmanager.exe` 23,579,136 B + `uninstall.exe` 127,302 B（2.1.5 安装时刻）+ 3 个 ico（运行时） | 2.1.5 payload 解压后总字节 ≈ **23,706,438 B ≈ 23.7 MB(十进制)** |
| **v2**：卸载器改为 Tauri 门面 + NSIS 内核（§15.1），`$INSTDIR` 变成 3 个程序文件 | 2.1.6 payload = `fontmanager.exe` + `uninstall.exe`（门面 ≈4.5 MB）+ `uninstall-core.exe`（内核 ≈0.13 MB）≈ **28.2 MB** |

**对 PRD K3 的修正**：PRD 说「≈ `fontmanager.exe` + 3 个 `.ico` + `LICENSE` + `uninstall.exe`」。实测**不含 3 个 ico、也不含 LICENSE**（`LICENSE ""`，见 0.2）。所以：
- 屏 1 「将写入 `{n}` 个文件」的 `{n}` = **3**（v2 从 2 改为 3；仍是"个位数"口径，符合 PRD D2 第 ③ 条）；
- 屏 1 「需要空间 约 420 MB」→ **约 29 MB**（v2 从 24 MB 上调，因为多了一个卸载器门面；PRD E2 已纠正方向，这里给精确来源）。

### 0.2 没有许可协议页（与规格书 §4.8 一致，比 PRD 描述的更确定）

- `installer.nsi:333-336`：`!if "${LICENSE}" != ""` → 才插入 `MUI_PAGE_LICENSE`；
- 本机渲染值 `rust-target/release/nsis/x64/installer.nsi:76` = `!define LICENSE ""` → **不插入**。

→ 安装器**不需要** EULA 流程，§6 的「与 EULA 的交互」答案就是「不存在」。

### 0.3 `EstimatedSize` 的加法是个**潜在既有 bug**，路线 B 天然避开

| 事实 | 出处 |
|---|---|
| 模板算法 = `GetSize($INSTDIR, /M=uninstall.exe)` + `ESTIMATEDSIZE` 常量 | `installer.nsi:1025-1028` |
| 本机渲染出的 `ESTIMATEDSIZE` = **23180** | `rust-target/release/nsis/x64/installer.nsi:100` |
| 本机已安装 2.1.5 的实测 `EstimatedSize` = **23150**（KB） | PowerShell 读 `HKCU\...\Uninstall\FontManager` |
| 23150 < 23180 → 若 2.1.5 也用同一常量，`GetSize` 必须是负数 | 矛盾 ⇒ 2.1.5 打包时该常量≈0（当时的 CLI 行为） |

→ **不要照抄 `GetSize + 常量`**。路线 B 直接写「本次实际写入字节 / 1024」= `23,579,136 / 1024` = **23,026 KB**，与 2.1.5 的 23150 差 **−0.54%**（在 PRD 附录 A 允许的 ±5% 内，类型与单位一致）。
（待核实、不阻塞：可用干净虚拟机跑一次 `FontManager_2.1.6_x64-setup.exe /S /NS /D=%TEMP%\zfm-probe` 后读该值，确认 23180 参与加法后的真实结果。**本机没有跑**——它会覆盖开发机上 2.1.5 的安装记录。）

### 0.4 注册表实测：13 值之外还有第 14 个值

PowerShell 读到的 `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\FontManager` 实际有 **13 个值**（与 PRD 附录 A 一致），另有：

| 位置 | 值 | 说明 |
|---|---|---|
| `HKCU\Software\IIEOzo\FontManager` | 默认值 = `C:\Users\...\AppData\Local\FontManager`（**不带引号**） | B2/B3 的唯一判据 |
| 同上 | `Installer Language` = `2052`（REG_SZ） | **PRD 附录 A 未列，但确实存在**；`un.onInit` 的 `MUI_UNGETLANGUAGE`（`installer.nsi:1078`）靠它决定卸载器界面语言 |

→ 新安装器**必须写** `Installer Language`（按解析出的 UI 语言写 `2052` 或 `1033`）。**不写 = 英文系统上卸载器变中文**（回退到第一个 `MUI_LANGUAGE`），这是 B-17 文案语言的隐性回归。

### 0.5 `.zfm-data-root` 的真实内容（B19 的追加语义有实证）

```
v=1
version=2.1.5
migrated=1 version=2.1.5 from=C:\Users\87557\AppData\Roaming\FontManager
```

第 3 行是主应用迁移成功后追加的（`store.rs:967` 附近）。安装器**只能以 `a` 模式追加**，任何情况下都不许重写这个文件——重写就把「这台机器迁过没有」的证据抹了（PRD B5 的验收用例正是这条）。

### 0.6 快捷方式的 AppUserModelId 必须精确写 `com.iieozo.fontmanager`

`utils.nsh:78-100` 的 `SetLnkAppUserModelId` 把 `PKEY_AppUserModel_ID` 设为 `${BUNDLEID}`；`BUNDLEID` = `com.iieozo.fontmanager`（`tauri.conf.json:5` 的 `identifier`）。**漏写 = 任务栏图标分组/固定项失效**：用户把图标钉在任务栏，升级后变成一个新的空白项。

### 0.7 运行中检测的真实语义（B10，可直接照抄）

`utils.nsh:24-69` 用的是 **RestartManager**：`RmStartSession` → `RmRegisterFile(exe)` → `RmGetList`；`ERROR_MORE_DATA` 即「有进程占用」。
- GUI：`MessageBox MB_OKCANCEL`（确定=强制关闭，取消=中止安装）
- `/S`：直接 `RmShutdown(RmForceShutdown)`；失败 → 控制台红字 + `Abort`
- `/P`：不弹窗，直接杀

→ 选型见 §4.0。**不用** `procs.rs` 的按名轮询做主判据（它看不见握着 exe 映像句柄的 `msedgewebview2.exe` 子进程）。

### 0.8 构建工具链的可用性（解掉 PRD U3）

| 事实 | 出处 |
|---|---|
| `makensis.exe` v3.11 在 `%LOCALAPPDATA%\tauri\NSIS\`，`Plugins\x86-unicode\additional\nsis_tauri_utils.dll` 也在 | 本机实测 |
| 渲染后的 include 目录（`utils.nsh` / `FileAssociation.nsh` / `SimpChinese.nsh` / `English.nsh`）由 `pnpm tauri build --bundles nsis` 落在 `rust-target/release/nsis/x64/` | 本机实测 |
| 现有 6 个 NSIS 安装包在 `rust-target/release/bundle/nsis/` | 本机实测 |

→ 预生成 `uninstall.exe` **不需要**新的工具链，只需一个 stub `.nsi` + 上面两条路径（§5）。

## 1. 方案总览

### 1.1 三个进程、两条链路

```
用户双击 / 更新器 -Wait             用户点「卸载」           用户双击图标
        │                                │                       │
        ▼                                ▼                       ▼
FontManager_<ver>_x64-setup.exe   <INSTDIR>\uninstall.exe   <INSTDIR>\fontmanager.exe
  （Tauri 安装器，本版新增）        （Tauri 门面，v2 新增）    （Tauri 主应用，不改）
                                  <INSTDIR>\uninstall-core.exe
                                    （NSIS 内核，v2 新增）
        │                                │                       │
        └──── 写 ──▶ <INSTDIR>/{fontmanager.exe, uninstall.exe, uninstall-core.exe, data\.zfm-data-root}
                     HKCU\Software\IIEOzo\FontManager  (默认值 = $INSTDIR)
                     HKCU\...\Uninstall\FontManager     (13 值 + Installer Language)
                     $SMPROGRAMS\FontManager.lnk  /  $DESKTOP\FontManager.lnk

另有**独立发布物**（不在本包里）：
FontManager_<ver>_x64-nsis-fallback.exe   兼容模式回退件（§14.3）
```

三条**必须成立**的跨进程契约（任何一条断了就是 PRD 里的 P0）：

| # | 契约 | 谁生产 | 谁消费 |
|---|---|---|---|
| C-a | `HKCU\Software\IIEOzo\FontManager` 默认值 = 安装目录（不带引号） | 安装器（§4.2） | `update.rs::recorded_user_install_dir()`（`update.rs:339-356`）→ `install_kind()` 返回 `PerUser`（`update.rs:392-413`）→ 一键更新存在与否 |
| C-b | `<INSTDIR>\data\.zfm-data-root` 存在 | 安装器（§4.5） | `store.rs::resolve_data_root()` 第 1 档锚点（`store.rs:487-504`）→ 数据根不横跳 |
| C-c | `<INSTDIR>\uninstall.exe` 存在且 `UninstallString` 指向它；它必须能找到同目录的 `uninstall-core.exe` | 安装器（§15.2） | 「应用和功能」+ 门面 → 内核；内核的 `SetContext` / `RestorePreviousInstallLocation`（`installer.nsi:1212-1216`） |

### 1.2 一次安装的完整时序

见 `docs/sequence-diagram-2.1.6-installer.mermaid`（含 GUI / `/S` / 取消 / 升级 / 「先卸载再装」五条支路）。三处关键顺序：

1. **WebView2 检测在 `tauri::Builder` 之前**（PRD D5/E7）。Tauri 窗口靠 WebView2 渲染，缺失时连错误页都画不出来。
2. **运行中检测在所有写盘之前**（`installer.nsi:960` 的位置）。
3. **注册表在所有文件写完之后**（`installer.nsi:997-1034`）——这是 `EstimatedSize` 依赖真实目录大小、以及「注册表存在 ⇒ 文件一定在」的隐含保证。反过来说：**注册表写失败 = 一个能跑但「应用和功能」里没有的程序**，所以注册表写入用「先算后写、失败重试 3 次」并把失败升级为 `ExitCode::RegistryOrShortcut`。

## 2. 包结构

### 2.1 结论：**三个 crate（一个 lib + 两个 bin）、不做 workspace 成员、前端只要一份**

v2 把原来单 crate 拆成三块，原因是卸载器必须与安装器**共用删除/注册表/快捷方式那套"系统集成"代码**，但**不能共用 payload**（安装器 30 MB，卸载器的 4.5 MB 不能背着它进 `$INSTDIR`）。

```
ZFontManager/
├─ installer-core/                ← 新增：纯 lib crate（**不依赖 tauri**，可被两个 bin 复用）
│  ├─ Cargo.toml                  package = "zfm-install-core"
│  └─ src/
│     ├─ lib.rs
│     ├─ payload.rs               内嵌 zip 的读取与逐条流式解压
│     ├─ registry.rs              13 值 + Installer Language + EstimatedSize（读 install-contract.json 生成物）
│     ├─ shortcut.rs              IShellLink + PKEY_AppUserModel_ID（COM）
│     ├─ apprunning.rs            RestartManager + 按父 PID 等 msedgewebview2 子进程
│     ├─ webview2.rs              pv 检测（只探测，装不装由调用方决定）
│     ├─ marker.rs                data\ 与 .zfm-data-root（追加写）
│     ├─ log.rs                   InstallLog（UTF-8 无 BOM / CRLF）
│     ├─ exit.rs                  ExitCode（§6.2）
│     └─ contract.rs              include!(concat!(env!("OUT_DIR"), "/contract.rs"))  ← build.rs 从 JSON 生成
├─ installer/                     ← 安装器 bin（依赖 installer-core）
│  ├─ Cargo.toml                  package = "zfm-installer"；`installer-core = { path = "../installer-core" }`
│  ├─ build.rs                    校验 payload.zip + 生成 contract.rs + 版本一致性断言（§3.4）
│  ├─ tauri.conf.json             frontendDist = "../dist-installer"，windows[0] 按规格书 §9.2
│  ├─ capabilities/default.json   只留 core:event / core:window 最小集
│  ├─ icons/icon.ico              复制自 src-tauri/icons/icon.ico（Alt-Tab 图标，A2）
│  ├─ manifest/install-contract.json   ← **唯一事实源**（§14.3.5）
│  ├─ payload/                    ← 构建产物（gitignore）
│  │  ├─ payload.zip              fontmanager.exe + uninstall.exe + uninstall-core.exe
│  │  └─ manifest.json            条目、大小、sha256、主程序 ProductVersion
│  └─ src/
│     ├─ main.rs                  启动闸门：argv → WebView2 → L1/L2/静默（§14.2）
│     ├─ args.rs                  CmdArgs 解析（§6）
│     ├─ plan.rs                  Plan / Mode / 目录判定 / 空间与可写预检
│     ├─ install.rs               Engine（§4.0 的 11 步 + 取消 + 重试）
│     ├─ journal.rs               写入清单 + 倒序回滚（**唯一允许删目录的地方**，§7.3）
│     ├─ progress.rs              Reporter trait + UiReporter + SilentReporter
│     ├─ native_ui.rs             L2 降级：MessageBoxW / TaskDialogIndirect / IProgressDialog
│     ├─ session.rs               单实例互斥体 + uninstalled_in_session
│     └─ bridge.rs                #[tauri::command]（§12.4）
├─ uninstaller/                   ← 卸载器 bin（依赖 installer-core，**无 payload**）
│  ├─ Cargo.toml                  package = "zfm-uninstaller"
│  ├─ tauri.conf.json             identifier 独立；`url: "installer.html?mode=uninstall"`
│  ├─ capabilities/default.json
│  └─ src/
│     ├─ main.rs                  argv → WebView2 探测 → 三屏 / 原生降级（§15.7）
│     ├─ confirm.rs               写 %TEMP%\zfm-uninstall-request.txt
│     └─ core_launcher.rs         spawn uninstall-core.exe /S；progress.txt 轮询
├─ installer.html                 ← 新增：Vite 第三个入口，**安装与卸载共用**
├─ src/installer/
│  ├─ main.ts                     四屏（install）/ 三屏（uninstall）状态机 + IPC + mock 回退
│  ├─ copy.ts                     COPY_ZH / COPY_EN（键名 = 规格书 §6 的 ZM_*）
│  ├─ installer.css               设计令牌（规格书 §3）+ 四屏布局（§4）
│  └─ ipc.ts                      invoke/event 封装 + isTauri() + mock.ts
├─ dist-installer/                ← 新增构建产物（独立 outDir）
```

**为什么不是 workspace 成员**：
1. 主应用 `src-tauri/Cargo.toml` 目前**没有** `[workspace]`，加一个 workspace 会把 200+ 依赖的解析范围整个换掉，`Cargo.lock` 要重解 —— 这属于「为了装一个安装器把主程序的构建链拆了」。
2. 三个 crate 之间用 **path dependency** 就能共享代码，不需要 workspace；`installer-core` 是纯 lib（不依赖 tauri），主编译面最小。
3. 共享同一 `target-dir`（各 crate 的 `.cargo/config.toml` 写 `target-dir = "../../../rust-target"`，与 `src-tauri/.cargo/config.toml` 一致）后，`tauri` / `serde` / `windows` 这些同名同版本依赖的编译产物可复用，第二个 bin 只为自己的代码付编译时间。

### 2.2 前端：复用同一套 Vite 工程，**不引入 React**

| 方案 | 结论 |
|---|---|
| A. 复用根 Vite 工程 + 第三个入口（`installer.html`），独立 `outDir` | ✅ **选它** |
| B. 在 `installer/` 下建第二个 Vite 工程（自己的 package.json / tsconfig / node_modules） | ❌ 第二份依赖树、第二份 tsconfig、两处锁文件漂移；`@fontsource-variable/inter` 还得装两遍 |
| C. 把四屏做成 React 组件塞进主 bundle 再用入口切 | ❌ 主 bundle 2.0 MB（`dist/assets` 实测 1,958,063 B），installer 入口会把 React 19 + MUI 风格层一起拖进来，与「安装器不该为 3 个图标背一个包」直接冲突（规格书 §7） |

**理由（逐条）**：
1. **有先例且已验证**：启动页就是这么做的 —— `vite.config.ts:19-28` 明确写「启动页是独立的第二个 HTML 入口（不是 React 应用的一部分）」，`tauri.conf.json:28-44` 用 `url: "splash.html"` 挂上去。安装器照抄这个模式，团队不需要学新东西。
2. **体积**：installer 入口只 import `copy.ts` / `ipc.ts` / `installer.css`，Rollup 按入口切 chunk，主 bundle 一行都不会进来。实测可用的字体子集：`inter-latin-wght-normal.woff2` + `jetbrains-mono-latin-wght-normal.woff2`（各 ≈40–70 KB），加 CSS/JS/图标，**installer 前端总产物体积预计 150–300 KB**。
3. **四屏的交互与动画不需要框架**：规格书 §3.4 要的是 CSS transition（340ms 淡入、900ms 进度条）、§4.6 的按钮规则是「一个主按钮 + 隐藏/显示」，§4.5 的日志区是「最多 5 行、新行插入、最老淡出」——全是 CSS + 40 行 TS。上 React 的收益是零，成本是 1.4 MB 与一次额外的构建入口配置。
4. **但确实需要 TS**：进度事件、取消竞态、二次确认、`/S` 与 GUI 的 UI 分支都在前端，所以是 **TS + CSS**，不是纯 HTML。

`vite.config.ts` 的改法（示意，不是最终代码）：

```ts
// 按 mode 切 outDir 与入口：主应用/splash 走 dist，安装器走 dist-installer
export default defineConfig(async ({ mode }) => {
  const isInstaller = mode === "installer";
  return {
    plugins: [react()],                                  // 安装器入口不 import React，插件在也不会进包
    build: {
      outDir: isInstaller ? "dist-installer" : "dist",
      emptyOutDir: true,
      rollupOptions: { input: isInstaller
        ? { installer: resolve(root, "installer.html") }
        : { main: resolve(root, "index.html"), splash: resolve(root, "splash.html") } },
    },
  };
});
```

`package.json` 加 `"build:installer": "tsc --noEmit && vite build --mode installer"` —— **不新增任何 npm 依赖**（`cross-env` 也不需要，`--mode` 是 Vite 原生参数）。

## 3. payload 打包与读取

### 3.1 选型：**zip 归档 + `include_bytes!` 内嵌**（唯一推荐）

| 候选 | 随机读 | 单文件 | 增量构建 | 完整性 | 结论 |
|---|---|---|---|---|---|
| **zip + `include_bytes!`** | ✅ 中央目录在内存切片上，零 syscall | ✅ | payload 变才重链安装器（一次发版一次） | ✅ Authenticode 覆盖只读段 | ✅ **选它** |
| 尾部追加归档（PE 尾挂 + footer） | ✅ 需 seek/read + 边界校验 | ✅ | ✅ 改主应用不用重编 | ⚠️ **必须 append 之后再签名**，顺序错=未签名发布 | ❌ 省下的是编译时间，赔上的是签名顺序这个易错点（PRD C3 是硬验收） |
| Tauri `bundle.resources` 放 exe 旁 | ✅ | ❌ 变两个文件 | ✅ | ❌ | ❌ 违反 D2 单文件 |
| `include_bytes!` + 自建格式（tar+zstd） | ⚠️ zstd 整帧/seekable 自己做 | ✅ | ✅ | ✅ | ❌ 多写 200 行且没有现成工具能打开排查 |

**为什么用 `zip` 而不是自造格式**：
- `zip` crate 已在主应用依赖里（`src-tauri/Cargo.toml:35`，`default-features = false, features = ["deflate"]`），版本与用法团队已经熟了；
- `ZipArchive::new(Cursor::new(PAYLOAD))` 只解析中央目录（几 KB，**<5 ms**），`by_index()` / `by_name()` 都可随机取；
- 出问题时可以用 7-Zip 直接打开 payload 检查（自造格式做不到）；
- 逐文件解压天然满足「每 1 个文件更新一次进度」（规格书 §4.5 屏 3）。

### 3.2 归档布局与压缩策略

| 条目 | 原始大小 | 建议压缩 | 说明 |
|---|---|---|---|
| `fontmanager.exe` | 23,579,136 B | `Deflated`（level 6） | PE 里已含压缩资源，实测收益通常 3–8%；解压 CPU ≈0.3–0.6 s |
| `uninstall.exe` | ≈127 KB | `Deflated` | NSIS 自带 LZMA 固实压缩，几乎无收益，但无害 |
| `manifest.json`（归档外） | — | — | 给 `build.rs` / CI / QA 读：条目、原始大小、sha256、主程序 ProductVersion |

**不做整包解压到 `%TEMP%`**：`installer.nsi:963` 的 `File` 指令本质是「从安装包流式解出」，我们保持同样的「流式直写目标目录」，中途取消时 `journal` 知道已经写了哪些（§7）。

### 3.3 体积与启动时间代价（明确数字）

| 项 | 值 | 依据 |
|---|---|---|
| payload 原始（v2：3 个文件） | ≈ 28.2 MB = `fontmanager.exe` 23,579,136 + 卸载门面 ≈4.5 MB + 内核 ≈130 KB | §0.1 实测 + 同类 Tauri 应用经验值；**打出真值后回填** |
| payload 压缩后（估） | 26.8–27.6 MB | 高熵 PE，deflate 收益 3–8%；**发出前用 `node tools/pack-payload.mjs` 打到 `manifest.json` 里，不靠猜** |
| 安装器自身（Tauri + 前端 + 图标） | 3.5–5.0 MB | 同类 Tauri release 应用经验值；**第一次构建后把真实值回填本文** |
| **最终 `*-setup.exe`** | **≈ 30–33 MB** | 仍与今天 `FontManager_2.1.5_x64-setup.exe`（≈26 MB）同量级；PRD D2「约 30 MB」成立 |
| 单独的 `uninstaller` exe（进 payload 的那个） | ≈ 4.5 MB | 它会被**压缩后**塞进 payload，所以最终只贡献 ≈4.3 MB |
| 冷启动到屏 1 首帧 | 目标 ≤ 800 ms（含 WebView2 初始化） | 与主应用启动页同量级；`include_bytes!` 不产生任何启动 IO |
| 屏 3 写盘（SSD，关实时保护） | ≈ 0.5–1.1 s（28 MB 顺序写 + deflate 解压） | 所以**进度动画（900ms/条）会成为观感瓶颈**，这是好事：不要为了"看起来久一点"加假延时 |

> 运行时 144 MB 不在包内（PRD K3 已核实：`src-tauri/resources/{python,node}-runtime` 实测 61 MB + 84 MB，release 另附 zip）。安装器**不得**假设 `<exe>\python-runtime` 存在，也**不得**去创建它。

### 3.4 构建期校验（build.rs，三条硬断言 + debug 开关）

1. `installer/payload/payload.zip` 存在，且能被 `ZipArchive` 打开；
2. 归档内**必须**恰好有 `fontmanager.exe`、`uninstall.exe`、`uninstall-core.exe` 三个条目（多/少都编译失败）——条目清单读 `install-contract.json`，**不在这里另写一份**（§14.3.5）；
3. `manifest.json` 里记的 `main_exe_product_version` 必须等于安装器 `CARGO_PKG_VERSION`（防止「装了 2.1.5 的 exe、写 2.1.6 的注册表」这种最难查的错）。

**debug 开关（lead 拍板第 2 点，结论：要，而且是"完全不 include"）**

| 构建 | payload 来源 | 为什么 |
|---|---|---|
| `release` | `include_bytes!("../payload/payload.zip")` | 单文件分发的要求（PRD D2） |
| `debug` | 从 `installer/payload/` **目录按条目名读盘**（`include_contract!` 里的名字 → 直接 `File::open`） | ① `include_bytes!` 24 MB 会让**每一次** payload 变动触发 24 MB 重链，UI 迭代时无法忍受；② 更重要的是 debug 下我们根本不需要 payload 存在 |

实现要点（否则开关等于没做）：
```rust
#[cfg(not(debug_assertions))]
static PAYLOAD: &[u8] = include_bytes!(concat!(env!("CARGO_MANIFEST_DIR"), "/payload/payload.zip"));
#[cfg(not(debug_assertions))]
fn open_archive() -> ZipArchive<Cursor<&'static [u8]>> { ZipArchive::new(Cursor::new(PAYLOAD)).unwrap() }

#[cfg(debug_assertions)]
fn open_archive() -> ZipArchive<BufReader<File>> {        // 直接读目录里的 payload.zip
    ZipArchive::new(BufReader::new(File::open(payload_zip_path())?)).unwrap()
}
```
`include_bytes!` 必须整条被 `#[cfg(not(debug_assertions))]` 包住 —— 只把**读取路径**分支是没用的，`include_bytes!` 仍然会把 24 MB 塞进 debug 产物并拖慢链接。同时在 debug 下 `build.rs` 只校验"目录里的文件在不在"，不校验大小（允许拿一个假的占位 zip 调试 UI）。

### 4.3 快捷方式：**COM `IShellLink` + `IPropertyStore`**

| 候选 | 能否设 AppUserModelId | 依赖 | 结论 |
|---|---|---|---|
| **`windows` crate 的 `IShellLinkW` + `IPersistFile` + `IPropertyStore`** | ✅ | 编译时间 +（一次性） | ✅ **选它** |
| `windows-sys` 手写 COM vtable | ✅ | 0 额外 crate，但 ~250 行 `unsafe` | ❌ 手写 vtable 出错是「运行期静默失败」类 bug |

写三个属性的顺序与 NSIS 完全一致（`utils.nsh:78-100`）：
`SetPath(<INSTDIR>\fontmanager.exe)` → `SetWorkingDirectory(<INSTDIR>)` → `SetIconLocation(exe, 0)` → `IPropertyStore::SetValue(PKEY_AppUserModel_ID, "com.iieozo.fontmanager")` → `Commit` → `IPersistFile::Save(lnk, TRUE)`。

- 开始菜单：`%APPDATA%\Microsoft\Windows\Start Menu\Programs\FontManager.lnk`（`STARTMENUFOLDER=""` → 不建子目录，`installer.nsi:1266`）

### 4.4 `data\` 与 `.zfm-data-root`（B19，逐行等价）

```
CreateDirectory(<INSTDIR>\data)                       // 2.1.5: CreateDirectory "$INSTDIR\data"
probe: File::create(<INSTDIR>\.zfm-data-probe)         // FileOpen ... w
  失败 → 只写日志、什么都不做（数据会回退到 %LOCALAPPDATA%\FontManager\data）
  成功 → remove_file(.zfm-data-probe)
       → OpenOptions::new().append(true).create(true).open(<INSTDIR>\data\.zfm-data-root)
       → 写 "v=1\r\n" 与 "version=2.1.6\r\n"
```

三条不许动的细节：
- **追加，不覆盖**（追加语义有实证，§0.5）；
- `\r\n`（与 NSIS 的 `$\r$\n` 一致）；
- 探针失败**不是错误**（`installer.nsi:46-47` 的语义：装不进去就回退，不中止安装）。

### 4.5 `EstimatedSize` 计算

```
bytes = Σ (本次写入 <INSTDIR> 的文件大小) - uninstall.exe 的字节数   // 沿用 2.1.5 的 /M=uninstall.exe 口径
kb    = (bytes + 512) / 1024          // 四舍五入
```

预期值：
- 2.1.5 实测 **23150 KB**（目录含 `fontmanager.exe` + `uninstall.exe`，排除后者 = 23,130 KB + 安装时刻的 exe 大小差）；
- **2.1.6 ≈ 27,5xx KB**（`fontmanager.exe` 23,579,136 + `uninstall-core.exe` ≈130 KB，排除 `uninstall.exe`）→ 比 2.1.5 **+19%**。

> ⚠️ **这会让 PRD 附录 A「允许 ±5% 差异」的口径不成立**，必须由产品确认新容差（§13 U11）。根因是"卸载门面从 130 KB 变成 4.5 MB"，属**真实占用变大**，不是计算错误 —— 改的应该是容差，不是数字。

### 4.6 `/R` + `/ARGS`（B9）

仅 `/S` `/P` 生效（`installer.nsi:1058-1069`）。GUI 路径由屏 4 的复选框决定。
实现：`std::process::Command::new(exe).args(split(run_args)).current_dir(instdir).spawn()`。
**已提权时的问题**：若用户「以管理员身份运行」安装器，直接 spawn 出的主应用也是管理员 → 它会尝试把 `data\` 写到需要提权的位置。缓解（P2，标注待确认）：检测到自身已提权时改用 `explorer.exe "<exe>"` 间接启动（以登录用户身份）。

## 5. 卸载器集成（**v2：本节已被 §15 取代，保留作为决策演进记录**）

> **v2 变更**：用户要求卸载界面与安装界面同一套 → 原「卸载器就是 NSIS 的 `uninstall.exe`，界面也是 NSIS 的」作废。
> 现行方案见 **§15**：`uninstall.exe` 变成 Tauri 门面，真正的删除由 `uninstall-core.exe`（NSIS 无页面内核）执行。
> 本节仍然有效的部分：**5.1 的"单源 + 共享 include"思路**（现在是内核的生成方式）、**5.2 的三个耦合点**（一条都没变）、**5.3 的「先卸载再装」用 `/P`**（改成调用门面但语义相同）。

### 5.1 预生成方案（解掉 PRD U3）

**单源 + 共享 include**，不复制粘贴：

```
新增 src-tauri/windows/uninstall-core.nsh     ← 从 installer.nsi 逐字搬出的卸载相关段
   · Var DeleteAppDataCheckbox / DeleteAppDataCheckboxState
   · MUI_UNCONFIRM 页 + un.ConfirmShow / un.ConfirmLeave（含 GetDpiForWindow/96 换算，原样）
   · MUI_UNPAGE_INSTFILES
   · Function un.onInit（SetContext / MUI_UNGETLANGUAGE / 读 /P /UPDATE）
   · Section Uninstall（:1091-1210 的全部内容，含 Delete "$INSTDIR\uninstall.exe"）
   · Function RestorePreviousInstallLocation / un.SkipIfPassive
新增 src-tauri/windows/uninstaller-stub.nsi   ← 只产出 uninstaller 的构建期 stub
修改 src-tauri/windows/installer.nsi          ← 用 !include "uninstall-core.nsh" 替换上述段落（**纯机械搬移**）
```

`uninstaller-stub.nsi` 的核心只有三行：

```nsis
OutFile "<建out>\uninstaller-stub.exe"        ; 只在构建期跑
Section
  SetOutPath  "$EXEDIR\harvest"
  WriteUninstaller "$EXEDIR\harvest\uninstall.exe"   ; 关键：写到 stub 自己旁边，不掉 $PLUGINSDIR
SectionEnd
```

构建步骤 `tools/gen-uninstaller.mjs`：

1. 渲染 stub 的 `!define` 组（与 `installer.nsi` 完全相同的名字与值：`PRODUCTNAME/MANUFACTURER/VERSION/MAINBINARYNAME/BUNDLEID/HOMEPAGE/INSTALLMODE/UNINSTKEY/MANUKEY/MANUPRODUCTKEY/ZFM_DATA_MARKER/STARTMENUFOLDER=""`）；
2. `!addincludedir "rust-target/release/nsis/x64"`（拿 `utils.nsh`）+ `!addplugindir "%LOCALAPPDATA%\tauri\NSIS\Plugins\x86-unicode\additional"`（拿 `nsis_tauri_utils.dll`）+ `!include "zfm-strings.nsh"`；
3. 调 `%LOCALAPPDATA%\tauri\NSIS\makensis.exe`（实测 v3.11 可用，§0.8）；
4. 静默跑一次 `uninstaller-stub.exe /S`，从 `harvest\uninstall.exe` 取产物 → `installer/payload/uninstall.exe`；
5. 打印产物 sha256 与大小（2.1.5 的同名产物为 127,302 B，可作为量级参考），写进 `manifest.json`。

> **顺序依赖**：stub 需要 `rust-target/release/nsis/x64/*.nsh`，这些由 `pnpm tauri build --bundles nsis` 渲染产生 → **「先跑一次 NSIS 打包（顺带产出兼容模式回退件），再预生成卸载内核」**。一次构建拿到三样东西：主程序 exe、回退件、卸载内核 —— 这是 §14.3 与 §15.1 能同时成立的原因。

### 5.2 安装器的三个耦合点（错一个就卸载不掉）

| 耦合点 | 要求 | 失败后果 |
|---|---|---|
| `MANUPRODUCTKEY` 默认值 | 必须写对且不带引号 | 卸载器 `SetContext`/`RestorePreviousInstallLocation` 找不到 `$INSTDIR` → 卸载删不到东西或删错目录 |
| `MAINBINARYNAME` | 卸载器 `Delete "$INSTDIR\fontmanager.exe"` 靠它（`installer.nsi:1101`） | 卸完留下 23 MB 的 exe |
| `BUNDLEID` | `DeleteAppUserModelId`（`installer.nsi:1139`） | 任务栏固定项残留 |

另外两条：
- **`uninstall.exe` 必须与安装器同一次构建、同一套签名**（PRD D4 风险 ①）。版本不同步的后果是「白名单口径漂移」——这是全项目最高风险代码（PRD R1）。
- **`uninstall.exe` 自己仍会自删**（NSIS 的 `_?=` 重定位机制），这是允许的；PRD D1 只禁止**安装器**自删。

### 5.3 「先卸载再装」（E4）

`ExecWait '"<INSTDIR>\uninstall.exe" /P'`

- `/P` 让 `un.ConfirmShow` 被 `Abort` 跳过（`installer.nsi:743`）→ `$DeleteAppDataCheckboxState` 保持空串 → `${If} ... = 1` 为假（IntCmp 空串算 0，见 `installer.nsi:420-428` 的注释）→ **保留数据** ✅
- 卸载器会删 `UNINSTKEY` 与 `$INSTDIR\fontmanager.exe`，但**不删 `MANUPRODUCTKEY`**（`installer.nsi:1185-1189` 在勾选分支里）→ 卸载后注册表仍记着旧目录
- 因此安装器必须在会话里置 `session.uninstalled_in_session = true`，让下一次 `Plan::detect()` 判为 `Mode::Fresh` + `instdir_pinned = true`：**目录仍钉住（不漂移），但允许回滚（因为此时没有"旧版本已部分覆盖"的风险）**

## 6. 静默 `/S` 与被动 `/P`

### 6.1 解析位置

`main()` 的第 1 步（早于 WebView2 检测，因为 `/S` 会改变后者的弹窗策略）：

```rust
let args = args::parse(std::env::args_os().skip(1));   // 无副作用、无 IO
webview2::ensure(args.silent)?;                        // 第 2 步
if args.silent { return silent_main(args); }           // 第 3 步：不进 Tauri event loop
tauri::Builder::default()...                           // 第 4 步：GUI
```

参数表（大小写不敏感，`/s` 也算；全角斜杠不认）：

| 参数 | 语义 | 备注 |
|---|---|---|
| `/S` | 全静默：零窗口、零 MessageBox、阻塞到装完 | **直接调用 `Engine::run()`，不创建任何窗口** |
| `/P` | 被动：跳过屏 1/屏 4，只保留屏 3 | P2；形态见 §13 U5 |
| `/D=<path>` | 强制目录，优先于注册表 | 必须最后一项、不加引号（NSIS 习惯）；含空格时**原样取剩余全部字符** |
| `/UPDATE` | 升级：不清理、不重建快捷方式、不装 WebView2 | 安装器自己不再需要它做清理（清理在卸载器里），但要**转发给卸载器**（E4 不用 /UPDATE） |
| `/NS` | 不建快捷方式（开始菜单 + 桌面） | |
| `/R` + `/ARGS=` | 装完即运行（仅 `/S` `/P`） | |

### 6.2 退出码语义

| 码 | 常量 | 含义 | 更新器行为 |
|---|---|---|---|
| 0 | `Ok` | 成功（含 GUI 用户取消？**不**——见下） | 删包 + 重启 |
| 1 | `UserCancel` | GUI 用户在屏 1/2 取消，或屏 3 取消并成功回滚 | 保留包 |
| 2 | `BadArgs` | `/D=` 非法（相对路径、盘符不存在）、参数冲突 | 保留包 |
| 3 | `NotWritable` / 空间不足 | 预检失败 | 保留包 |
| 4 | `AppRunning` | 主程序运行中且强制结束失败 | 保留包 |
| 5 | `PayloadCorrupt` | 归档校验/解压/写盘失败 | 保留包 |
| 6 | `RegistryOrShortcut` | 注册表写入失败（重试 3 次后） | 保留包 |
| 7 | `WebView2Failed` | WebView2 下载/安装失败 | 保留包 |
| 8 | `UpgradeInterrupted` | 升级路径中途中断（**不回滚**，PRD §3.3） | 保留包 |
| 9 | `AnotherInstance` | 已有安装器实例 | 保留包 |
| 10 | `WebviewBoot` | Tauri 窗口/前端引导失败（兜底） | 保留包 |

**用户取消 = 1 而不是 0**：PRD §3.1 说「退出码 0（用户取消 ≠ 失败）」是针对**手动双击**的语义；但 `update.rs` 只把 0 当成功（`update.rs:976` `$p.ExitCode -eq 0` → 删包）。两条要求冲突时**以更新器安全为准**：取消返回非 0，宁可让用户多点一次，也不能让更新器在"没装"的情况下删包并重启旧版（那正是 PRD R5/P0 描述的事故）。→ **待用户确认（§13 U1）**：GUI 首次进入时若检测到是更新器启动（父进程是 PowerShell），可把取消码改成 0。倾向：**不改，统一返回 1**。

### 6.3 与 EULA / 重启的交互

- **EULA**：不存在（§0.2）。安装即同意 GPL-3.0，文案在屏 2 底部一句话（规格书 §4.8）。
- **重启**：从不重启机器。唯一「重启」是 WebView2 安装成功后 **re-exec 自身**（`std::process::Command::new(current_exe).args(同 argv)` + `exit(0)`）。

### 6.4 `/P` 的 P2 降级方案

最小实现：**复用同一窗口与同一套 DOM**，只把状态机从 `[Welcome, Location, Installing, Finish]` 收窄为 `[Installing]`：
- 窗口仍 1000×620（不做第二套尺寸，省掉 100% 的设计工作量）；
- 屏 3 的「取消安装」在 `/P` 下隐藏（无人值守，取消没有意义）；
- 装完自动关窗，退出码同上。

不做的事：不复用屏 1/4 的 DOM 片段去拼一个「小进度窗」——`/P` 目前无调用方（PRD Q5），多一套布局只是维护成本。

## 7. 升级覆盖与取消

### 7.1 状态机

```mermaid
stateDiagram-v2
    [*] --> Boot
    Boot --> WebView2Check: argv 解析完成
    WebView2Check --> Boot: 装好 WebView2 → re-exec
    WebView2Check --> Silent: 缺失且 /S（静默装失败 → exit 7）
    WebView2Check --> Welcome: 已具备

    Silent --> Preflight: exit 7 / exit 2
    Preflight --> Engine: 通过
    Preflight --> Fail34: 不可写 / 空间不足（exit 3）

    Welcome --> Location: 继续（只读则直接可用）
    Location --> Welcome: 返回
    Welcome --> UninstallThenReinstall: 点「先卸载再装」
    UninstallThenReinstall --> Welcome: 卸载器返回（session.uninstalled_in_session=true）
    Location --> Preflight: 点安装
    Preflight --> Installing: 通过
    Preflight --> Location: 不可写 / 空间不足（屏 2 红字，主按钮禁用）

    Installing --> Engine
    Engine --> Finish: 成功（Fresh 与 Upgrade 相同）
    Engine --> RolledBack: 取消（仅 Mode::Fresh）
    Engine --> Interrupted: 取消/失败（Mode::Upgrade，**禁止回滚**）
    Engine --> Retryable: 单步失败（屏 3 + 重试）

    RolledBack --> [*]: exit 1
    Interrupted --> [*]: exit 8 + install.log
    Retryable --> Engine: 点「重试」（复用同一 Plan）
    Retryable --> RolledBack: 点取消（仅 Fresh）
    Finish --> [*]: exit 0（可选 spawn 主程序 + 建桌面快捷方式）
    Fail34 --> [*]: exit 3
```

### 7.2 「升级路径禁止回滚」的代码级落点（PRD R4 的硬规则）

不靠注释，靠**类型系统 + 唯一入口**：

1. `Journal` 只能由 `Journal::open_fresh(instdir)` 构造，而 `InstallEngine::new()` 里写死：
   ```rust
   let journal = match plan.mode {
       Mode::Fresh | Mode::FreshAfterUninstall => Some(Journal::open_fresh(&plan.instdir)?),
       Mode::Upgrade => None,          // ← 升级路径根本不持有回滚能力
   };
   ```
2. `rollback()` 是 `impl Journal` 的方法，**不是 `Engine` 的方法** → `Mode::Upgrade` 下编译期就拿不到 `Journal`，写不出「顺手回滚」。
3. `Journal` 的删除动作只有三个原语，**删目录一律非递归**：
   - `remove_file(path)` —— 只删 `written_files` 里的、且必须是 `plan.instdir` 的子孙（`path.starts_with(&instdir)`，路径先 `canonicalize` 再比，防 `..` 与junction 逃逸）；
   - `remove_dir(path)` —— **`std::fs::remove_dir`（非递归）**。目录非空时它必然失败，**这就是"只删空目录"的物理保证**，不需要任何 `is_empty` 预判；
   - `prune_empty_parents(path)` —— 从被删文件的父目录起往上，逐个 `remove_dir`，遇到非空即停（同样靠 `remove_dir` 的失败语义）。
4. **`remove_dir_all` 在本设计里被彻底取消（不是"限定一处"，而是零处）**。
   理由：`Journal` 只记录**本次创建**的目录与**本次写入**的文件，而写入的每个文件都在 `written_files` 里 —— 所以"先删文件、再删目录"就够了，不需要递归删除。
   CI 红线改为：`grep -rn "remove_dir_all" installer*/src uninstaller/src` **必须零命中**（比"恰好 1 处"更好判定、也更安全）。
   **万一将来确实需要删整棵子树**（例如 `data\` 里我们建的探测子目录），必须满足**全部四条**才允许调用，且只能出现在 `journal.rs` 一处：
   - ① 目标目录在 `created_dirs` 里（本次 `create_dir` 建的，不是"已存在"）；
   - ② `fs::symlink_metadata(target)?.file_type()` **既不是 symlink 也不带 `FILE_ATTRIBUTE_REPARSE_POINT`**（防 junction 把我们带到 `C:\`）；
   - ③ `fs::read_dir(target)?.next().is_none()` 为真（**确认为空**）—— 注意这条与"非递归 remove_dir"的语义重复，但它是**显式可读的安全断言**，代码评审时一眼能看懂；
   - ④ `target.canonicalize()?.starts_with(plan.instdir.canonicalize()?)`。
   > 判定"空"的方法就是 ③：`read_dir` 取第一个条目，`None` 即空。**不要**用 `path.read_dir()?.count() == 0`（等价但会遍历完整个目录，`data\` 里有 1.7 MB 账本时会明显变慢）。

### 7.3 全新安装的写入清单倒序清理（PRD §3.3）

- 清单文件：`%TEMP%\FontManager-install-journal.json`，**JSONL 追加写**（崩溃时前缀仍可解析），每写一个文件前 `record_write` + `flush`（本次只有 2 个文件，代价可忽略）；
- 记录内容：`{"v":1,"mode":"fresh","instdir":"…","version":"2.1.6","created_dirs":[…],"written_files":[…]}`；
- 取消时：`written_files` **倒序** `remove_file` → `created_dirs` **倒序** `remove_dir`（非空自动跳过）→ 删 journal；
- **绝对不做**：`remove_dir_all(<INSTDIR>)`、删 `data\`、删 `字体库\`（用户可能已经放东西进去，PRD §3.3 明令禁止）。
- 崩溃后残留：下次启动在屏 1 检测 journal 存在且 `instdir == 本次 plan.instdir` → 状态行加一行「检测到上次安装未完成，将先清理残留」，在开始安装时先按同样规则清理；`instdir` 不匹配则**只记日志、不动手**。

## 8. 失败与恢复：六种异常态归谁

| # | 场景 | 责任层 | 落点 | 用户看到什么 |
|---|---|---|---|---|
| E1 | 无写入权限 | **安装器 · plan** | `Plan::preflight()` 的写探针（`installer.nsi:637-648` 等价） | 屏 2 路径框下红字 + 主按钮禁用（规格书 §4.7 ①） |
| E2 | 空间不足 | **安装器 · plan** | `GetDiskFreeSpaceExW(INSTDIR 的卷)` vs `payload.total_uncompressed` | 屏 2 副状态位 |
| E3 | 安装失败 | **安装器 · engine** | 单步 `Err` → `ProgressEvent{stage:"error"}` | 屏 3 状态行 + `重试`（日志保留） |
| E4 | 已安装（升级） | **安装器 · plan** | `Mode::Upgrade` | 屏 1 状态行上方提示 + 「先卸载再装」 |
| E5 | 文件被占用 | **安装器 · apprunning** | RestartManager 判定 + 写失败归类 | 屏 3「fontmanager.exe 正在运行，请关闭后重试」 |
| E6 | 静默/被动 | **安装器 · 模式分支** | `silent_main()` | 无界面 |
| E7 | WebView2 缺失 | **安装器 · main 第一段** | `webview2::ensure()` | 原生 MessageBox（**唯一允许的模态框**）+ 官方源安装 + re-exec |
| E8 | 数据迁移失败 | **主应用首启** | `store.rs::migrate_to_data_root`（`store.rs:781`） | 主应用的报错；安装器**不重试、不清理、不搬动** |

统一原则（照抄 PRD §4）：安装器进程**永不**弹原生模态框，除 E7 —— **v2 例外**：L2 降级态（§14.2）与卸载器的 WebView2 缺失降级（§15.7）也用原生框，因为那时确实没有可用的 HTML 界面。`/S` 与 `/P` 下一律写日志 + 退出码。

> **卸载方向的六种失败场景不在本节**，见 §15.6（那份表覆盖了"门面被杀""内核被删到一半""文件被占用""U2 无取消"等）。

**安装器崩溃后的残留**：
1. `journal`（§7.3）是唯一凭据，只含「本次写的」；
2. 半写的 `fontmanager.exe` 会被下一次安装直接覆盖（幂等），不需要预先处理；
3. 注册表要么没写（崩溃在步骤 7 之前）、要么全写（步骤 7 内部用「先构造全部键值再逐条写」把窗口缩到最小）；后者崩溃会留下「卸载项齐全但文件不全」—— 下次安装会重写同一批值，无害；
4. **不做**「安装完自动修复」这类隐式行为；只做「提示 + 可重跑」。

## 10. 任务列表（**7 个**，按依赖顺序）

> **为什么从 5 个变成 7 个**：v2 的两条用户硬需求（回退链、卸载器换界面）各自是一个完整子系统 —— T06 要动 `installer.nsi` 的注册表段并把"两套产物必须一致"做成可执行校验，T07 要新写一个 bin + 保住白名单等价性。把它们塞进 T04/T05 会让单个任务超过 2500 行、验收点超过 15 条，失去"一次交给一个人能落地"的性质。

  6. U2 期间**没有**取消按钮（DOM 断言），且进度数字与 `progress.txt` 行数一致；
  7. 装→卸→重装 后 `install_kind` 仍返回 `PerUser`（W16）。

## 14. 回退链（v2 新增：用户硬需求一）

> **本节取代 PRD Q2 的「NSIS 转内部应急」结论。** 新结论：NSIS 包是**正式发布物**，语义是「Tauri 安装器跑不起来时仍能完成安装」。
> 相关的旧章节已回改：§0.1（payload 文件数）、§2.1（crate 结构）、§3.3（体积）、§9（文件清单）、§10（任务）、§13（待定项）。

### 14.1 先把两个故障面拆开（它们对策完全不同）

| 面 | 具体触发 | 现状后果 | 对策 |
|---|---|---|---|
| **A. 安装器 UI 起不来** | ① 目标机缺 WebView2 ② `webviewInstallMode` 下载失败（国内网络 / 代理 / 组策略） ③ 杀软拦掉 WebView2 安装器 ④ Tauri 前端崩 | 用户双击**没反应**（最坏体验：连"失败"都不知道） | §14.2 的三档降级 |
| **B. 连进程都起不来** | ⑤ 整个 exe 被 SmartScreen/杀软拦（阻断执行） ⑥ 下载损坏 ⑦ 用户系统版本过低 | 同上 | §14.3 的独立回退件 + 可发现路径 |

**关键洞察：A 和 B 的边界是"exe 有没有跑起来"。** 只要 exe 跑起来了（A 的全部情况），我们**一定能装上**——因为安装内核（`Engine`）不依赖 WebView2（§6.1 的进程结构红利：`/S` 本来就不进 Tauri event loop）。B 才需要第二个文件。

### 14.2 故障面 A：三档降级（L1 → L2 → L3）

| 档 | 界面 | 触发条件 | 体积代价 |
|---|---|---|---|
| **L1** | 四屏 Tauri UI | WebView2 可用 | 0（本来就要） |
| **L2** | **原生 `IProgressDialog` + 原生 MessageBox** | WebView2 缺失 / 下载失败 / `tauri::Builder` 返回错误 | **0 字节**（`IProgressDialog` 是 Win32 自带 COM，无新依赖） |
| **L3** | 无（用户自己下载回退件） | L2 也失败（内核报错 / 目标目录不可写且用户拒绝换） | 另一个发布物，不在本包内 |

**L2 的具体行为**（这是本轮最重要的补强，它把"没反应"变成"能装上"）：

1. `webview2::ensure()` 返回 `Err` → **不退出**，改为进 L2；
2. 原生 `MessageBoxW(YESNO)`：「安装程序无法显示界面（缺少 Microsoft Edge WebView2）。可以用兼容模式继续安装：没有进度界面，但会完成同样的安装。是否继续？」+ 一个「打开 WebView2 下载页」的第三选项（用 `TaskDialogIndirect` 或两个连续 MessageBox 实现，倾向 `TaskDialogIndirect`：三按钮 + 命令链接，Win8+ 都有）；
3. 用户选「继续」→ 起 `IProgressDialog`（`CLSID_ProgressDialog`），把 `SilentReporter` 的进度回调接到 `IProgressDialog::SetLine`/`SetProgress64`，跑**与 L1 完全相同**的 `Engine::run()`；
4. 结束 → `IProgressDialog::Stop()` → 成功用一个极小 MessageBox 告知「安装完成」，失败则 MessageBox 显示错误码 + 日志路径。

**为什么不用"内置固定版本离线 WebView2 包"**：Evergreen Standalone Installer 约 **180 MB**，要塞进 26 MB 的单文件安装包 → 体积 ×7。明确否决（PRD D5 风险 ③ 已表态）。
**为什么不用"极小原生 bootstrap + 再拉 Tauri exe"**：那是把单文件拆成两个文件，与 D2 直接冲突，且多一层退出码转发（PRD D3 明确反对）。我们的安装器**本身**就是"4 MB 的壳 + 24 MB payload"，再套一层壳没有任何收益。

### 14.3 故障面 B：独立回退件（NSIS）的设计

#### 14.3.1 发布物命名与分工

| 文件 | 形态 | 角色 | 用户看到的名字 |
|---|---|---|---|
| `FontManager_2.1.6_x64-setup.exe` | Tauri 安装器 | **默认**，一键更新只认它 | 「FontManager 2.1.6 安装程序」 |
| `FontManager_2.1.6_x64-nsis-fallback.exe` | 现有 NSIS 模板产物（`installer.nsi` + `hooks.nsh`，本就在仓库里能出包） | **兼容模式**：无 WebView2 / Tauri 包被拦 / 用户手动选择 | 文件名里带 `nsis-fallback`，release 正文标注「兼容模式安装包」 |

#### 14.3.2 「两个 setup 会不会让更新器挑错」——机制，不是提醒

三条机制**叠加**，任何一条都足以保证不挑错：

1. **文件名后缀**：`update.rs::pick_setup()` 只收 `name.to_ascii_lowercase().ends_with("-setup.exe")`（`update.rs:222`）；`-nsis-fallback.exe` 结尾是 `-fallback.exe` → **硬过滤**，连候选都进不了。这是 PM 定的机制，也是唯一不引入概率的机制。
2. **不动挑选逻辑**：我们**不**改 `pick_setup` 去"支持两个包"。一旦改成"两个都认然后排序"，就把确定性换成了概率（而概率会随 release 资产上传顺序变化）。
3. **CI 断言**：`release.yml` 增加一条硬断言——`release/` 目录里 `*-setup.exe` 必须**恰好 1 个**（PRD C1 已有），`*-fallback.exe` 必须**恰好 1 个**；两者都不满足就 `throw`。

> 副作用（要写进发布说明）：`update.rs` 的候选集里从此永远只有 1 个文件，`pick_setup` 的 `rank`（`contains("x64")`）分支实质上退化 —— 这是**好事**，少一条会漂的逻辑。

#### 14.3.3 用户怎么知道该用回退件（三个可发现的位置）

| 时机 | 手段 |
|---|---|
| Tauri 包跑到 L2 且 L2 也失败 | MessageBox 里直接给两个出口：① 打开日志所在目录 ② 打开 releases 页面（`ShellExecute` 到 `HOMEPAGE/releases/latest`） |
| 双击后**完全没反应**（B 类） | 安装器无机会自救。靠 ① release 正文的「兼容模式安装包」一段 ② README/`docs` 里的排障段 ③ 发布页把 fallback 放在**第二个**位置并写明用途（不是隐藏） |
| 用户已经装上了但更新失败 | `apply-update.log`（`update.rs:918` 起）与主应用「检查更新」的失败提示里，加一句「可到发布页下载兼容模式安装包」——**这需要改主应用文案（1 行）**，标 P1 |

**能否"安装器崩溃后自举到 NSIS"**：**不能，而且不要做**。自举要求"回退件也在同一个 exe 里"= 单文件里塞两套安装器（+26 MB），且崩溃时未必有能力再拉起任何东西。L2 已经把"能装上"这件事覆盖住了；L3 只需要"用户看得见"。

#### 14.3.4 硬约束 F2：两条路径的产物必须逐项相同

这是 PM 的 F2，也是"用回退装的版本更新不了 / 变成两套"的唯一防线。**必须逐项相同**：

| # | 项 | 校验手段 |
|---|---|---|
| 1 | `$INSTDIR` 递归文件清单 | `(relpath, size, sha256)` 有序 JSON；**排除** `data\`（含 `install.log` 时间戳）与 `字体库\`（运行时生成/用户资产） |
| 2 | 注册表 13 值 + `Installer Language` | 有序 JSON（键、值名、类型、值），类型必须一致（`REG_DWORD` ≠ `REG_SZ`） |
| 3 | `install_kind()` | 在装好的机器上跑主应用，读 `update` 诊断日志里的 `install_kind=user` |
| 4 | 快捷方式 | Target / WorkingDirectory / IconLocation / `PKEY_AppUserModel_ID` 四项 |
| 5 | `uninstall.exe` 等卸载件 | `ProductVersion` == 2.1.6，且签名状态一致（PRD C4） |

**校验脚本**：`tools/verify-install-parity.mjs`（P0，T06 交付）
- 输入：两台机器/两个快照点的 `snapshot-install.json`
- 输出：逐项 diff；**任何一条不同即 fail**，并打印差异路径
- 快照生成：`tools/snapshot-install.ps1`（文件哈希 + 注册表导出 + `.lnk` 解析）

**F6（互覆盖）**：先 `fallback` 装 → 再 `Tauri` 装（`/S`）→ 断言 `$INSTDIR` 文件数不变、`data\` 与 `字体库\` 的 `(count, mtime)` 不变、注册表值不变。反向再来一遍。这条能抓出"两条路径的默认目录/目录判定不一致"这类隐蔽 bug。

#### 14.3.5 单一事实源（U7 的答案）

**问题**：目录结构 + 13+1 个注册表值，Rust 侧与 NSIS 侧都各写一份 → 必然漂移（PM 的 R7）。

**方案：`installer/manifest/install-contract.json` 作为唯一事实源**，三个消费者：

| 消费者 | 生成方式 | 漂移防护 |
|---|---|---|
| Rust 安装器 | `build.rs` 读 JSON → `OUT_DIR/contract.rs`（`const REGISTRY_VALUES: &[RegValue]`、`const PAYLOAD_FILES: &[&str]`） | 编译期常量，改值必须改 JSON |
| Rust 卸载器 | 同一个 lib crate 复用同一份 `contract.rs` | 同上 |
| NSIS 回退件 | `tools/gen-nsis-contract.mjs` → `windows/install-contract.nsh`（`!insertmacro ZFM_WRITE_CONTRACT_REGISTRY`），`installer.nsi` 用 `!include` **替换** `:1013-1034` 的手写块 | 生成物入库 + CI 断言"重新生成后 git diff 为空"；且**首次替换必须做逐字 diff 证明等价** |

`install-contract.json` 的字段（示例，值全部取自附录 A）：

```json
{
  "version_field": "2.1.6",
  "payload": [
    { "name": "fontmanager.exe", "exclude_from_estimated_size": false },
    { "name": "uninstall.exe",   "exclude_from_estimated_size": false },
    { "name": "uninstall-core.exe", "exclude_from_estimated_size": false }
  ],
  "registry": {
    "product_key": { "root": "HKCU", "key": "Software\\IIEOzo\\FontManager",
                     "values": [ { "name": "", "type": "REG_SZ", "value": "{INSTDIR}" },
                                 { "name": "Installer Language", "type": "REG_SZ", "value": "{LCID}" } ] },
    "uninstall_key": { "root": "HKCU", "key": "Software\\Microsoft\\Windows\\CurrentVersion\\Uninstall\\FontManager",
                       "values": [ { "name": "DisplayIcon", "type": "REG_SZ", "value": "\"{INSTDIR}\\fontmanager.exe\"" } ] }
  },
  "shortcuts": [{ "where": "startmenu", "name": "FontManager.lnk", "target": "{INSTDIR}\\fontmanager.exe" }],
  "estimated_size": { "exclude": ["uninstall.exe"] }
}
```

> ⚠️ `estimated_size.exclude` 里的 `uninstall.exe` 是**历史口径**（NSIS `GetSize ... /M=uninstall.exe`）。2.1.6 起 `$INSTDIR` 有 3 个程序文件，但**仍只排除 `uninstall.exe`**，以尽量贴近 2.1.5 的可比性（见 §13 U11 的容差问题）。

### 14.4 缺陷 1：回退件必须满足退出码契约（P0，决定回退件是否合格）

**现状（已核实，真实存在）**：

| 缺陷 | 证据 | 后果 |
|---|---|---|
| `/S` 下仍弹模态框 | `installer.nsi:589`（`MessageBox` 未包 `${If} ${Silent}`）、`installer.nsi:943`（WebView2 安装失败提示） | 无人值守安装**永久挂住**，更新器 `-Wait` 一起挂 |
| 失败也返回 0 | 全模板**无 `SetErrorLevel`**；`installer.nsi:944` 是裸 `Quit` | `update.rs:976` 判定「ExitCode -eq 0」→ **删包 + 重启旧版**，用户下次启动还是旧版 |

**修法（T06）**：
1. 每个「致命分支」前 `SetErrorLevel 1`（非致命告警仍返回 0）；
2. `:589` / `:943` 的 MessageBox 包上 `${IfNot} ${Silent}`；
3. `Quit` 改为在该分支前置 `SetErrorLevel`，或直接 `SetErrorLevel 1` + `Quit`。

**验证方法（必须写进 QA 用例）**：
- 构造必失败场景：`setup.exe /S /D=<一个不可写目录>`（如 `C:\Windows\System32\zfm-probe`）→ 断言 ① 进程退出码 **≠ 0** ② `EnumWindows` 期间**零新窗口** ③ `%TEMP%\FontManager-install.log`（或 NSIS 的 `DetailPrint` 落点）有原因行；
- 再构造 `/S` + 缺 WebView2 → 断言零窗口、非 0 退出（而不是卡住）。

### 14.5 缺陷 2：选包器的版本比较（P1，进 T05）

| 缺陷 | 证据 | 修法 |
|---|---|---|
| 选包比的是枚举顺序，不是版本 | `release.yml:144` `Get-ChildItem ... | Select-Object -First 1`；`update.rs:241-244` 的 `rank` 只判 `contains("x64")`，同级保留"先到的" | ① `release.yml` 侧：`Sort-Object Name -Descending` 或直接按 `${VERSION}` 精确匹配（**工程师已在改**）；② `update.rs` 侧：`rank` 改为 `(x64, 版本号)` 二元组，用现有的 `parse_version`（`update.rs:1084` 附近）比较，**同级才比名字** |

> 本机 `rust-target/release/bundle/nsis/` 里躺着 2.1.1–2.1.6 六个包，这就是这条会咬人的现场；但**发布流水线在干净 runner 上跑**，所以真实风险在"本地手工打包上传"（P1）。

### 14.6 缺陷 3 的核实结论（不沿用转述）

lead 问的是「用户中途取消/安装失败时，`data` 目录已迁移一部分会怎样」。**核实结论：这个场景不存在。**

| 事实 | 证据 |
|---|---|
| 安装器**从不迁移任何数据**，只建 `data\` 目录 + 探针 + 追加标记 | `hooks.nsh:42-60`，全macro 内无 `Rename`/`CopyFiles`/`Delete` 任何用户数据 |
| 迁移只发生在**主应用首启** | `store.rs:781` `migrate_to_data_root(&mut notes)` 是主应用模块，安装器进程里根本没有这段代码 |
| 迁移自身的"搬了一半"有专门保护 | `store.rs:308` `MIGRATE_MARKER = ".zfm-migrate-in-progress"`；`store.rs:493-498` 把该标记也作为 `data_root` 的锚点，注释写明「必须继续锚在这里重试」 |
| 迁移策略是 copy 不 move、失败原地不动 | `store.rs:781` 起的实现（ADR-D4），旧位置副本保留 |

→ 2.1.6 **不需要**为这条做任何设计。真正相关的"中断"风险转移到了**新卸载器**（§15.7）。

## 15. 卸载器（v2 新增：用户硬需求二 —— 界面与安装器同一套）

> **本节取代 PRD 原 D4 的「卸载界面沿用 NSIS」。** 白名单逻辑仍然**一行不改**，改的只是"谁来做门面"。
> 相关回改：§5（保留为决策演进记录）、§9、§10、§13。

### 15.1 形态选型：三个 crate、两个 bin、**共用同一套前端**

| 候选 | 白名单改动 | 体积 | 自删 | WebView2 缺失 | 结论 |
|---|---|---|---|---|---|
| A. 安装器二进制加 `--uninstall` | 0 | **+26 MB 进 `$INSTDIR`**（要带 payload 才能卸载） | 难 | ❌ | ❌ `EstimatedSize` 直接翻倍；PRD D4 已否决 |
| B. 独立 Tauri 卸载器 + **Rust 重写白名单** | **重写**（PRD N2/R1 红线） | 4–5 MB | 可 | 需另做原生兜底 | ❌ 把最高风险代码重写一遍，收益只是"好看" |
| C. 独立 Tauri 卸载器（门面）+ **NSIS 无页面内核**（原白名单原地不动） | **0** | 4.5 MB + 0.13 MB | 由内核负责（NSIS 内建） | ✅ 门面起不来时直接跑内核 | ✅ **选它** |
| D. 复用主应用 `fontmanager.exe --uninstall` | 0 | 0 | ❌ 自己就是待删文件（dropper） | ❌ 主应用同样依赖 WebView2 | ❌ PRD D4 已否决 |

**C 方案的关键点：门面不决定删什么。** 删除集合永远由 `hooks.nsh` + `Section Uninstall` 决定；UI 只负责①问用户"要不要删数据"②画进度③画结果。**宁可进度不准，也不让 UI 参与决定删除范围。**

#### 15.1.1 目录与 crate 结构（回改 §2.1）

```
FontManager/
├─ installer-core/          ← 新增：纯 lib crate（不依赖 tauri）
│  └─ src/{payload,registry,shortcut,journal,marker,apprunning,webview2,log,exit}.rs
├─ installer/               ← 安装器 bin（依赖 installer-core）
│  └─ src/{main,args,plan,install,session,bridge,silent,native_ui}.rs
├─ uninstaller/             ← 卸载器 bin（依赖 installer-core，**不含 payload**）
│  └─ src/{main,confirm,native_fallback,core_launcher}.rs
├─ installer.html           ← 两个 bin **共用的唯一前端入口**
└─ src/installer/           ← 共用前端代码
   ├─ main.ts               （按 `?mode=install|uninstall` 切换四屏/三屏）
   ├─ copy.ts / installer.css / ipc.ts
```

- **不建 workspace**（理由同 §2.1），用 **path dependency**：`installer/Cargo.toml` 与 `uninstaller/Cargo.toml` 都写 `installer-core = { path = "../installer-core" }`。
- **为什么共用前端**：用户要求"和安装界面一样的界面设计"。共用同一份 CSS/HTML 是**唯一**能保证"以后改一处不会两处漂移"的形式（规格书 §1.1 讲路线 A 时正是这个理由）。卸载器只需要在 `main.ts` 里换一屏序列 + 换文案表。
- `uninstaller` 的 `tauri.conf.json`：`identifier` = `com.iieozo.fontmanager.uninstaller`（**不要与安装器/主应用共用**，否则 WebView2 用户数据目录打架）；窗口同上（1000×620、无标题栏、透明、圆角，规格书 §9.2）；`url: "installer.html?mode=uninstall"`；`frontendDist: "../dist-installer"`（同一份产物，零额外构建）。

### 15.2 进程与自删链（卸载器最难的工程点）

`$INSTDIR` 里从此有 **3 个程序文件**（回改 §0.1）：

| 文件 | 是什么 | 谁删它 |
|---|---|---|
| `fontmanager.exe` | 主应用 | 内核（`installer.nsi:1101`） |
| `uninstall.exe` | **卸载器门面**（Tauri，≈4.5 MB）—— `UninstallString` 指向它（附录 A 的值**不变**） | 内核（`installer.nsi:1130` 已有这一行） |
| `uninstall-core.exe` | **卸载内核**（NSIS，无页面，≈130 KB，构建期由 stub 生成） | 内核自己（新增一条 `Delete`） |

```
用户点「卸载」(控制面板 / 设置→应用 / UninstallString)
  └─ uninstall.exe（门面，Tauri）
       ├─ 检测 WebView2 → 有：三屏 UI ；无：§15.7 原生降级
       ├─ 屏 U1 确认（复选框「同时删除全部数据与字体库」默认不勾）
       ├─ 写 %TEMP%\zfm-uninstall-request.txt  （一行：delete_data=0|1）  ← 跨进程传参
       ├─ spawn uninstall-core.exe /S  （**不等待**，门面随后退出）
       └─ exit(0)                                        ← 门面自己退出，别锁住自己的 exe
uninstall-core.exe（NSIS 内核）
  ├─ un.onInit：读 request.txt → 赋 $DeleteAppDataCheckboxState
  ├─ 等门面 pid 退出（OpenProcess + WaitForSingleObject，上限 15s）
  ├─ Section Uninstall（**原封不动**）：CheckIfAppIsRunning → 删程序文件 → 删注册表 → hooks 白名单
  ├─ 删 $INSTDIR\uninstall.exe（:1130 已有）与 $INSTDIR\uninstall-core.exe（新增）
  ├─ RMDir "$INSTDIR"（:1135，非递归：有 data\字体库 时失败＝预期）
  └─ 自删：NSIS 默认机制（门面用 `Exec` 而非 `ExecWait "_?=$INSTDIR"`，内核会复制自身到
     %TEMP% 再运行，因此能删掉 $INSTDIR 里那个"原始的自己"）
```

四条要点：
1. **`UninstallString` 值不变**：仍是 `"$INSTDIR\uninstall.exe"`（附录 A 第 7 行）→ PRD B-1 逐字节一致不受影响。
2. **门面不自删**：门面只 `exit(0)`，自删交给内核。这样门面不需要复制自身到 `%TEMP%`（少一个 dropper 特征）。
3. **内核的自删是 NSIS 内建行为**，不是新写的代码：只要启动时**不带** `_?=$INSTDIR`，NSIS 会把自己复制到 `%TEMP%` 再跑。今天的 2.1.5 卸载器本来就是这套机制，风险不变。
4. **`/S` 与直接执行内核**：`uninstall-core.exe /S` 就是 2.1.5 卸载器在静默模式下的等价物 —— 这条路径**不经过任何 Tauri 代码**，是 §15.7 降级的基础。

### 15.3 卸载 UI 的三屏（视觉一律引用规格书）

| 屏 | 版式来源 | 内容 | 按钮 |
|---|---|---|---|

### 15.4 白名单等价性：怎么"证明"（本设计最关键验收项）

#### 15.4.1 为什么一行都不改 `hooks.nsh`

R1（写错一次 = 删用户字体）与 N2（卸载白名单口径不许变）是项目最高优先级约束。方案 C 的**全部价值**就在于：删除集合仍然由那份跑了 15 个版本、被 PRD B-18 逐条核实过的代码产生。**凡是"重写白名单"的路线，无论测试多严，都是在把已验证的东西换成未验证的东西。**

#### 15.4.2 唯一改动的三处（都在"删什么"之外）

| 改动 | 为什么必须改 | 风险控制 |
|---|---|---|
| 新增 `Delete "$INSTDIR\uninstall-core.exe"` | 多了这个文件，不删就是残留 130 KB | 属"删我们自己的程序文件"同类扩展（`installer.nsi:1101/1130` 的邻居），golden test 显式覆盖 |
| `un.onInit` 增加：读 `%TEMP%\zfm-uninstall-request.txt` → `StrCpy $DeleteAppDataCheckboxState` | 复选框的决定在前一个进程（门面）里做 | 只在**文件存在**时才覆盖；`/S` 下文件不存在 → 保持空串 → 保留数据（与 2.1.5 完全一致） |
| `un.onInit` 增加：等门面 pid 退出（上限 15s） | 否则内核删不掉正在运行的门面 | 超时后继续（此时那次 `Delete` 失败，U3/日志会提示重试） |

#### 15.4.3 golden test：用"两个二进制跑同一批用例，快照 diff 为空"来证明等价

`tools/uninstall-golden/`（T07 交付）：

| 组成 | 内容 |
|---|---|
| **用例** | **W1–W12**（PM 已列，覆盖 `hooks.nsh` §1–§2.5 全量）+ **W13**（删 `uninstall.exe`）+ **W14**（删 `uninstall-core.exe`）+ **W15**（`/UPDATE` 下 14 项全部不执行） |
| 每个用例的预置 | 在隔离根 `%TEMP%\zfm-golden\<case>\` 下构造：`data\{state.json 或空}`、`字体库\`、`plugins\`、`python-runtime\`、`%APPDATA%\FontManager`（含/不含特征文件两版）、`%APPDATA%\ZFontManager`、`%LOCALAPPDATA%\com.theholyonez.fontmanager`、`%TEMP%\fontmanager-*.zip`、HKCU Fonts 值（指向 `字体库\` / `C:\Windows\Fonts\` 各若干）、`Software\Classes\.S-FontManager` 等 |
| **金标准** | 2.1.5 的 `uninstall.exe` 二进制（**已存在于仓库历史/本机安装目录**，127,302 B）→ 跑 `/S`（勾选与不勾选两种） |
| **被测** | 新的 `uninstall-core.exe` → 同样两种 |
| **快照器** | `tools/snapshot-tree.mjs`（递归 `(relpath, size, sha256)`，**跳过 mtime**）+ `tools/snapshot-registry.ps1`（把 4 个相关键导出为有序 JSON，含值类型） |
| **判据** | 15 个用例 × 2 种模式 = 30 次快照 diff **全部为空** |
| **反向注入** | 从内核里故意删掉一条 `RMDir /r "$APPDATA\FontManager"` → golden test **必须失败**。这条证明"测试本身不是空跑"，比 30 个通过更重要 |

**运行环境**：必须在**干净 Windows VM/runner**（`windows-2025`）上跑，因为用例会真的动 HKCU。`release.yml` 之外单独开一个 `uninstall-golden.yml`，PR 到 `installer/` / `uninstaller/` / `windows/` 时触发。

#### 15.4.4 UI 的进度从哪来（精度与安全解耦）

- 内核在 `un.onInit` 之后、`Section Uninstall` 之前，**先枚举一遍**"将要处理的项目"写 `%TEMP%\zfm-uninstall-plan.txt`（一行一项，`file|path` / `dir|path` / `regv|path|name`）；
- 门面（或 L2 的 `IProgressDialog`）读这个文件得到**分母**；
- 内核每处理一项，`FileWrite` 一行到 `%TEMP%\zfm-uninstall-progress.txt`；门面每 100 ms tail 一次 → 真实进度；
- **plan 文件只影响进度数字，不参与删除决策**。若 plan 与执行不一致（模板改了但枚举那段忘了改），最多是进度条不准 —— **不会错删**。这是本设计最重要的一条解耦。

### 15.6 失败与中断（卸载方向）

| 场景 | 行为 | 依据 / 理由 |
|---|---|---|
| 门面在写 request 前被杀 | **什么都没删** | 最安全：所有动作都在内核里 |
| 门面写完后、内核起来前被杀 | 内核照跑（已 spawn，父进程死了不影响） | `std::process::Command` 默认不杀子进程 |
| 门面在前台挂着不退出 | 内核等 15s 后继续；删门面失败 → 记日志，U3 提示"重启后手动删除" | 有界等待，不无限挂 |
| 内核删到一半被杀 | 已删的**不恢复**；注册表删除在文件之后（模板顺序），所以残留形态是"程序文件残缺 + 注册表还在" | **卸载是幂等的**：重跑 `uninstall.exe`（若还在）或 `uninstall-core.exe /S` 即可继续；对已不存在的目标 `Delete`/`RMDir /r` 是 no-op |
| 目标文件被占用 | ① 主应用：`Section Uninstall` 开头就有 `CheckIfAppIsRunning`（`installer.nsi:1097`）→ GUI 弹框 / `/S` 强制关；② `msedgewebview2.exe` 子进程：内核加一段有界等待（复用 §0.7 的"按父 PID 等子进程"）；③ 仍然失败的文件：跳过 + 计数 + 写日志 | ① 是现状；② 新增（P1，行为增强，需 QA 验证不会误杀别的 WebView2 宿主）；③ 保守 |
| U2 期间用户想中断 | **不提供取消**（PM 已定） | 中断 = 半删状态，比"多等 20 秒"更糟；Windows「应用和功能」本身也不给取消 |
| `/S` 卸载失败 | 非 0 退出 + 日志，**不弹窗** | 与缺陷 1 同一契约（内核 stub 里加 `SetErrorLevel`） |

> 补一条与"备份/回滚"的关系（回应 §14.6）：卸载**没有**备份，也不应该做。`data\` 的删除是**用户显式勾选**的（文案已写「全部数据与字体库」），这是 2.1.5 已披露的行为，不改。

### 15.7 WebView2 不可用时的降级（PM 的硬门槛）

**这是"卸载器不能变成纯 Tauri 应用"的落点。**

```
uninstaller main()
  ├─ argv 含 /S 或 /P 的 /S 分支  ──────────────▶ 直接 spawn uninstall-core.exe /S，自己不建窗口
  └─ 交互模式
       ├─ webview2::detect()（只看不装 —— 卸载时不该往系统里加东西）
       ├─ 有 → 建 Tauri 窗口，三屏
       └─ 无 → 原生 MessageBoxW（YESNO）
                标题「卸载 FontManager」
                正文「无法显示卸载界面（系统缺少 Microsoft Edge WebView2）。
                      可以继续卸载，但不会显示进度；你的数据与字体库将被保留。
                      是否继续？」
                ├─ 是 → IProgressDialog + spawn uninstall-core.exe /S（不带 delete_data）
                │        → 结束 MessageBox「已卸载。数据与字体库已保留。」
                └─ 否 → exit(1)（什么都没删）
```

三条要求都满足：
1. **不需要 WebView2 也能卸载完**（走内核 `/S`）；
2. **降级路径本身也过白名单等价测试**（它就是 W1–W15 的被测对象之一 —— golden test 直接测内核，不测门面）；
3. **不往用户系统装东西**（卸载时不装 WebView2，只降级）。
